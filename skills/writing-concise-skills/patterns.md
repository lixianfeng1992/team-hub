# Patterns — 技法与模式

## 写责任，别写步骤
**When to use**: 任何 prompt / skill / system prompt 的写作
**How**: 给目标、边界、验收标准（责任状），把路线和实现留给模型；"给弱模型写步骤，给强模型写责任"
**Trade-offs**: 强模型下收益巨大；弱模型下仍需步骤

## 12 行样板
**When to use**: 开始写一个新 skill
**How**: 目标 —— 12 行就够，一张截图放得下，三句话讲明白
**Trade-offs**: 样板太小会失去信息量；先小后大、按需扩展

## 补上下文 + 守门槛（双职责检查）
**When to use**: 评估一个 skill 值不值得写
**How**: 问两问 —— 它补了什么上下文？它守了什么门槛？—— 都答不上就不写
**Trade-offs**: 只补上下文不守门槛 → 无约束；只守门槛不补上下文 → 变监控

## 渐进式披露
**When to use**: 内容多到放不进主文件
**How**: 主文件只留核心框架，细节按需加载（章节文件、规范文件）；代码审查时才加载审查规范
**Trade-offs**: 主文件更精炼；需要建立索引和加载约定

## 门槛前置（Gate-first）
**When to use**: 错误代价高的环节（如调试、发布）
**How**: 先定义"通过"标准，不满足标准不许前进；如 diagnosing-bugs：没有稳定、快速、能明确变红的验证方式，就不许猜原因
**Trade-offs**: 提高质量下限；可能拖慢探索节奏

## 追问逼共识（grill-me 式）
**When to use**: 需求不清晰、边界未对齐时开工前
**How**: 只聊需求不聊实现；不断追问目标、边界、取舍，把"大概这样"逼成可执行共识
**Trade-offs**: 追问过载会拖垮流程（Pocock 自己停用）；控制问题数量和时机，考虑窄场景压力测试定位

## 元理论 + 单品组合
**When to use**: 发布和传播 skill
**How**: 单品负责出圈（12 行可展示的），元理论负责留人（方法论文章）；用自己的渠道反复推
**Trade-offs**: 有产品无理论 → 用户没有留下来的理由；有理论无单品 → 没有传播钩子

## 两周检验清理
**When to use**: 评估已安装的 skill
**How**: 装进流程两周后还在用的留下，积灰的删掉；拥有不算数，用起来才算数
**Trade-offs**: 可能误删低频高价值 skill；配合触发记录判断
